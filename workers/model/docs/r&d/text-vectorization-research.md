# Research: векторизация текста для ModelWorker (Worker №8)

**Задача:** выбор архитектуры векторизации текста до начала реализации
**Статус:** черновик для обсуждения командой

> ModelWorker сегодня работает с уже готовыми векторами: L2-нормализация,
> косинусная близость, пороговая классификация (`workers/model/ModelWorker.h`).
> Векторизация (превращение текста в эмбеддинг) — самая тяжёлая операция
> пайплайна (CPU/GPU-инференс нейросети), поэтому подход к ней фиксируется
> отдельным research до написания кода.

## Краткое решение (TL;DR)

Рекомендуемая архитектура — **гибрид «векторизация при вызове + точный
hashmap-кэш»** (предложение Никиты принято в усиленном виде):

1. **Источник эмбеддингов — внешний embedding-сервис по HTTP API**
   (OpenAI-совместимый `POST /v1/embeddings`), вызываемый **изнутри
   ModelWorker** через собственный HTTP-клиент за интерфейсом
   `EmbeddingBackend`. Вариант «через HTTP-воркер» отклонён как основной
   (нарушает принцип самодостаточности Worker и требует переделки Executor),
   но оставлен как fallback-сценарий интеграции.
2. **Векторизация — при каждом вызове (on-the-fly), но через точный кэш**
   `hash(текст + модель) -> вектор` с LRU-вытеснением и ограничением памяти.
   Предвычисление (offline) — только для статичных корпусов, как отдельный
   режим, не как основной путь.
3. **Ключ кэша — XXH3-128** (внутри доверенного процесса) либо SHA-256
   (если тексты могут поступать от недоверенного источника).

---

## 1. Контекст и постановка

ModelWorker отвечает за capability «model»: нормализация вектора, косинусное
сходство двух векторов, классификация по порогу. Все три операции предполагают,
что текст уже превращён в числовой вектор. Следующий шаг развития воркера —
замкнуть цепочку `текст -> эмбеддинг -> normalize -> cosine/classify` внутри
одной capability, не нарушая архитектурный принцип SADER: **Worker является
источником истины для своей capability**, а `Executor` не должен содержать
специальной логики под конкретные Worker'ы.

Векторизация вычислительно несопоставима с остальными операциями воркера:
L2-нормализация 384-мерного вектора — это ~384 делений, микросекунды; прогон
текста через трансформер — миллисекунды даже на GPU и десятки миллисекунд на
CPU. Порядки по данным бенчмарков: `all-MiniLM-L6-v2` (22,7 млн параметров,
384 измерения) выдаёт ~190–200 текстов/с на 24-ядерном CPU Ryzen 9 7900X,
~263 текстов/с на Apple M2 Max и ~3000 текстов/с на потребительской
RTX 2080[^1^]; даже медленная потребительская GPU ускоряет инференс примерно
в 40 раз по сравнению с одним ядром CPU, а для крупных моделей класса
E5-large одиночный запрос на одном ядре CPU легко превышает 100 мс[^2^].
Именно этот разрыв и делает выбор архитектуры векторизации значимым решением:
ошибка здесь умножается на каждый вызов воркера.

В рамках research рассматриваются: (а) два варианта архитектуры по времени
векторизации — предварительное сохранение векторов vs векторизация при каждом
вызове; (б) оптимизация через hashmap-кэш текстов и векторов; (в) два варианта
интеграции источника эмбеддингов — через HTTP-воркер как отдельную capability
и через API внутри ModelWorker; (г) несколько вариантов оптимизации с выбором
итогового.

## 2. Источник эмбеддингов: где и как считать вектор

Независимо от того, когда векторизовать (заранее или на лету), нужно выбрать,
*кто* выполняет инференс. Рассмотрены три варианта: делегирование
HTTP-воркеру, собственный HTTP-клиент внутри ModelWorker и локальный инференс
в процессе.

### 2.1. Вариант В1: эмбеддинг как API через HTTP-воркер

Идея: `HttpWorker` уже существует как capability выполнения HTTP-запросов
(`workers/http/HttpWorker.h`). ModelWorker мог бы не знать про сеть вообще:
Executor оркестрирует цепочку «HttpWorker вызывает embedding-сервис →
ModelWorker получает вектор». Внешний сервис — Hugging Face Text Embeddings
Inference (TEI), Ollama или любой OpenAI-совместимый endpoint. TEI —
production-ready Rust-сервер с токен-базированным динамическим батчингом,
Flash Attention, образами для CPU и GPU и эндпоинтами `/embed`,
`/v1/embeddings`, `/rerank`, `/predict`[^3^][^4^]. Ollama предоставляет
`/api/embed` с нативным батчингом и OpenAI-совместимый `/v1/embeddings`;
переход с последовательных одиночных запросов на батч даёт ~2,4× ускорение
индексации[^5^][^6^].

Плюсы варианта: переиспользование готовой capability, чистое разделение
ответственности, соответствие философии SADER «каждая операция — Worker».
Минусы существеннее: в текущем интерфейсе `Worker` нет механизма вызова
одного Worker'а из другого — оркестрацию цепочки пришлось бы добавлять в
`Executor`, что прямо нарушает запрет на worker-specific логику в ядре;
каждый вызов векторизации превращается в два сетевых/межпроцессных хопа
(Executor→HttpWorker→сервис) вместо одного; обработка ошибок (таймауты,
ретраи, недоступность сервиса) размазывается по двум воркерам.

### 2.2. Вариант В2: эмбеддинг по API внутри ModelWorker

Идея: ModelWorker сам содержит HTTP-клиент и ходит в embedding-сервис
(TEI/Ollama/облачный API) по OpenAI-совместимому контракту
`POST /v1/embeddings` с полями `model`, `input` (строка или массив строк),
`encoding_format` (`float`/`base64`)[^7^]. Детали транспорта прячутся за
внутренним интерфейсом `EmbeddingBackend`, так что смена сервиса или переход
на локальный инференс не меняют публичный контракт воркера (схему
аргументов).

Плюсы: Worker остаётся самодостаточным и самоописываемым — вся информация о
capability, включая зависимость от внешнего сервиса, сосредоточена в нём;
один сетевой хоп; ретраи/таймауты/выбор модели — локальная ответственность
воркера; Executor не трогаем вообще. Минусы: дублирование части
функциональности HttpWorker (HTTP-клиент появится в двух местах), воркер
обрастает конфигурацией (endpoint, модель, ключи, таймауты). Дублирование
снимается тем, что HTTP-часть оформляется как узкий клиент под один
контракт `/v1/embeddings`, а не как универсальный клиент.

### 2.3. Вариант В3 (альтернатива на будущее): локальный инференс в процессе

ONNX Runtime имеет C++ API, и существуют готовые обвязки: например,
`libembedding` — C/C++ библиотека с нативным C++-токенизатором (WordPiece/BPE
через `tokenizer.json`), требующая только ONNX Runtime ≥ 1.16[^8^]. Это самый
быстрый путь (~5 мс на текст для MiniLM-класса моделей на CPU) и единственный
полностью офлайн-вариант, но он тянет в проект тяжёлую зависимость
(ONNX Runtime, веса модели ~80–90 МБ), усложняет сборку и лицензирование
артефактов. Важный нюанс из практики: ONNX-экспорт sentence-transformers
отдаёт токен-эмбеддинги, поэтому pooling и L2-нормализацию нужно
реализовывать самостоятельно[^9^] — для нас это не страшно, `normalize()` в
ModelWorker уже есть. Отдельный практический урок от Manticore: на CPU
батчинг текстов разной длины может *замедлять* инференс из-за «налога на
паддинг» — работа растёт как `batch × max_len`, поэтому батч-оптимизации
нужно проверять замером, а не по учебнику[^10^]. Вариант оставлен как
эволюция за тем же интерфейсом `EmbeddingBackend`.

### 2.4. Сравнение вариантов источника эмбеддингов

| Критерий | В1: через HTTP-воркер | В2: API внутри ModelWorker | В3: локальный ONNX |
|---|---|---|---|
| Латентность на запрос | 2 хопа, ~15–25 мс | 1 хоп, ~4–15 мс | ~5 мс (CPU MiniLM) |
| Изменения в Executor | Требуются (оркестрация) | Не требуются | Не требуются |
| Самодостаточность Worker | Низкая (логика в 2 местах) | Высокая | Высокая |
| Зависимости сборки | Нет новых | HTTP-клиент (уже есть в проекте для HttpWorker) | ONNX Runtime + веса (~90 МБ) |
| Работа без сети | Нет | Нет (кроме кэша) | Да |
| Масштабирование инференса | Отдельный сервис, GPU-нода | Отдельный сервис, GPU-нода | Только ресурсы процесса SADER |
| Ошибки/ретраи/таймауты | Размазаны по 2 воркерам | Локальны воркеру | Локальны воркеру |
| Соответствие архитектуре SADER | Спорное (цепочки в Executor) | Полное | Полное |

**Промежуточный вывод:** основной вариант — **В2** (OpenAI-совместимый HTTP
API изнутри ModelWorker за интерфейсом `EmbeddingBackend`); В1 — fallback для
сценариев, где embedding-сервис уже развёрнут и политика запрещает воркерам
собственные исходящие соединения; В3 — дорожная карта для офлайн-режима.

## 3. Когда векторизовать: предварительно или при каждом вызове

### 3.1. Вариант А: предварительная векторизация с сохранением

Все тексты векторизуются заранее (при загрузке корпуса или отдельной
batch-задачей), векторы сохраняются (файл, БД, векторное хранилище), а
ModelWorker при вызове только читает готовый вектор. Это общепринятая
практика для поисковых систем: документы принято эмбедить офлайн, а онлайн
оставлять только эмбеддинг запроса — тогда онлайн-путь состоит из одного
вызова эмбеддинга и одного поиска по векторам[^11^]. Предвычисление
амортизирует тяжёлый инференс: он выполняется один раз в офлайне, а
поисковые запросы работают с готовыми векторами без обращений к модели[^12^].

Плюсы: минимальная и предсказуемая латентность вызова (чтение из памяти/диска
~мкс–мс), возможность массовой векторизации на GPU с батчингом (батчи десятков
и сотен текстов обрабатываются почти без роста латентности на текст[^13^]),
повторные вызовы бесплатны. Минусы: нужен контур хранения и синхронизации
(где лежат векторы, кто их обновляет), устаревание при изменении корпуса или
смене модели — векторы разных моделей несравнимы, при смене модели весь
корпус векторизуется заново[^14^]; для динамических текстов (пользовательский
ввод, изменяющиеся документы) предвычислить невозможно в принципе.

### 3.2. Вариант Б: векторизация при каждом вызове

Каждый вызов ModelWorker с текстом сам выполняет эмбеддинг через выбранный
источник (раздел 2). Плюсы: векторы всегда свежие и соответствуют текущей
модели, не нужно хранилище и синхронизация, схема работы одинакова для
статичных и динамических текстов. Минусы: каждый вызов платит полную стоимость
инференса + сетевой хоп — по оценкам, HTTP на localhost добавляет порядка
5–20 мс на round trip, gRPC/unix-сокеты 1–8 мс, тогда как обращение к памяти
процесса — наносекунды[^15^][^16^]; повтор одного и того же текста (типично
для пороговой классификации и сравнения с эталонами) сжигает ресурс впустую;
при недоступности сервиса воркер полностью неработоспособен.

### 3.3. Сравнение

| Критерий | А: предварительно | Б: при каждом вызове |
|---|---|---|
| Латентность вызова | ~мкс–мс (чтение) | ~4–150 мс (инференс + сеть) |
| Свежесть при смене модели/текста | Устаревает, нужна переиндексация | Всегда актуально |
| Динамические тексты | Не покрывает | Покрывает |
| Инфраструктура | Хранилище векторов + пайплайн загрузки | Только доступ к сервису |
| Повторные вызовы | Бесплатны | Полная стоимость каждый раз |
| Отказоустойчивость | Работает при упавшем сервисе | Нет |

**Промежуточный вывод:** ни один вариант в чистом виде не подходит как
единственный. Для ModelWorker как capability общего назначения (вызывается
по запросу, тексты потенциально динамические) базовым путём выбирается
**вариант Б, усиленный кэшем** (раздел 4); вариант А остаётся поддерживаемым
режимом для статичных корпусов — фактически это тот же кэш, заполненный
заранее (прогрев).

## 4. Оптимизация: hashmap-кэш эмбеддингов (предложение Никиты)

### 4.1. Точный кэш `текст -> вектор`

Предложение Никиты: хранить в hashmap соответствие «текст → полученный
вектор» и не векторизовать повторно то, что уже считали. Это классический
exact-match кэш, и для эмбеддингов он особенно эффективен: в отличие от
генеративных LLM-ответов, эмбеддинг — детерминированная функция текста и
модели, поэтому точное совпадение входа даёт корректный повторно
используемый результат всегда. В литературе по кэшированию LLM exact-match
критикуют за низкий hit rate на произвольных промптах[^17^], но профиль
вызовов ModelWorker иной: эталонные тексты для `cosine`/`classify` и типовые
входы повторяются постоянно, и именно их кэш и поглощает.

Стоимость промаха и попадания различаются на 4 порядка: попадание —
наносекунды–микросекунды (обращение к `unordered_map` в памяти), промах —
единицы–десятки миллисекунд[^15^][^16^]. Эффект на среднюю латентность
нелинеен (см. график в разделе 5): hit rate 90 % снижает среднюю латентность
в 10 раз, 99 % — в ~100 раз.

### 4.2. Ключ кэша: хеш текста + идентификатор модели

Хранить сами тексты как ключи расточительно (длинные строки, дорогое
сравнение), поэтому ключ — хеш. Выбор функции:

| Хеш | Скорость | Стойкость к коллизиям | Когда применять |
|---|---|---|---|
| XXH3-64/128 | ГБ/с на ядро, скорость порядка пропускной способности RAM | Только от случайных коллизий; злоумышленник может сконструировать коллизию | Тексты из доверенного контура; XXH3-128 снимает birthday-bound 64-бит (~2³² записей)[^18^] |
| SHA-256 | ~0,5–2 ГБ/с на ядро | 128-бит стойкость, практических коллизий нет | Тексты могут поступать извне (потенциально недоверенный источник)[^18^] |
| `std::hash<std::string>` | Максимальная | Реализационно-зависим, нестабилен между сборками | Только для in-memory кэша без персистентности |

В ключ обязательно включается **идентификатор модели и версия конфигурации**
(`model`, `dimensions`, препроцессинг): эмбеддинги разных моделей живут в
разных пространствах и несравнимы[^14^], поэтому смена модели должна давать
другие ключи, а не перетирать кэш.

### 4.3. Политика вытеснения и ограничение памяти

Кэш без границ — утечка памяти. Рассмотрены политики: LRU (вытеснение
самого давно использованного), LFU (по частоте), TTL (по времени жизни).
Исследование политик вытеснения для кэшей эмбеддингов показывает, что
реальные рабочие нагрузки чаще частотно-смещённые, и варианты LFU в среднем
лидируют[^19^], но LFU сложнее и хуже переживает смену паттерна трафика
(«прогретые» записи блокируют новые). Для ModelWorker выбирается **LRU с
жёстким лимитом по памяти** (по умолчанию, например, 256 МБ) плюс опциональный
TTL — просто, предсказуемо, достаточно для частотно-смещённой нагрузки;
переход на LFU — обоснованная эволюция, если замеры покажут низкий hit rate.

Оценка памяти (384 измерения, класс all-MiniLM-L6-v2):

| Текстов в кэше | float32 (1536 Б/вектор) | int8 (384 Б/вектор) |
|---|---|---|
| 1 000 | ~1,5 МБ | ~0,4 МБ |
| 100 000 | ~154 МБ | ~38 МБ |
| 1 000 000 | ~1,5 ГБ | ~384 МБ |

Скалярное int8-квантование сокращает память ровно в 4 раза при потере качества
обычно менее 1 %[^20^] и рассматривается как опция второго этапа: для порогов
кэша до ~100 тыс. записей float32 проще и достаточен. Потолок в 256 МБ — это
~170 тыс. текстов в float32 или ~680 тыс. в int8.

### 4.4. Почему не семантический кэш (на этом этапе)

Семантический кэш (GPTCache и аналоги) ищет не точное совпадение, а
«достаточно похожий» запрос по эмбеддингу[^17^][^21^]. Для ModelWorker это
неприменимо концептуально: сама операция воркера — *вычислить* эмбеддинг,
а семантический кэш требует эмбеддинг запроса *до* поиска в кэше — то есть
мы бы сначала векторизовали текст, чтобы понять, нужно ли его векторизовать.
Плюс семантический кэш вносит ложноположительные попадания (для
классификации по порогу это недопустимо) и требует векторного индекса.
Отклонено; может быть переоценено, если появится capability «ответить на
похожий вопрос», но не для вычисления самого вектора.

Амортизация предвычисления для статичного корпуса: 1 млн коротких текстов
(~30 токенов) — ~1,4 ч на 24-ядерном CPU, ~5–6 мин на RTX 2080[^1^], либо
порядка $0,60 через облачный API класса text-embedding-3-small
($0,02/1M токенов)[^23^]. Вывод: даже крупный статичный корпус
векторизуется за минуты–часы, поэтому прогрев кэша (вариант А) дёшев и
реализуется батч-вызовами того же `EmbeddingBackend`.

## 6. Рассмотренные варианты оптимизации

| № | Вариант | Суть | Эффект | Вердикт |
|---|---|---|---|---|
| О1 | Точный hashmap-кэш (Никита) | `XXH3/SHA-256(текст+модель) → вектор`, LRU, лимит памяти | 10–100× при hit rate 90–99 % | **Принят (ядро решения)** |
| О2 | Прогрев кэша (offline-предвычисление) | Батч-векторизация статичного корпуса заранее тем же backend | Убирает промахи для известных текстов | **Принят как режим** (вариант А через О1) |
| О3 | Батчинг запросов к сервису | Накопление текстов в один `input: [...]` | ~2,4× на индексации[^5^] | Принят для batch-API воркера; для одиночных вызовов неприменим |
| О4 | int8-квантование векторов в кэше | 1536 Б → 384 Б на запись | 4× памяти, <1 % качества[^20^] | Отложен (этап 2, по замерам памяти) |
| О5 | Держать векторы L2-нормированными | Нормализация один раз на записи в кэш | `cosine` сводится к dot product; согласуется с `normalize()` | **Принят** (Ollama и TEI уже умеют отдавать нормированные векторы[^6^][^3^]) |
| О6 | Keep-alive + таймауты/ретраи в HTTP-клиенте | Постоянное соединение к сервису | Снимает ~100–200 мкс на установку соединения, стабилизирует p99[^16^] | **Принят** |
| О7 | Семантический кэш | Поиск похожего запроса по вектору | Неприменим/вреден для этой задачи | Отклонён (раздел 4.4) |
| О8 | Локальный ONNX-инференс | Убрать сеть совсем | ~5 мс/текст, офлайн | Дорожная карта (В3), тяжёлая зависимость |
| О9 | Статические эмбеддинги (model2vec) | Таблица lookup + усреднение вместо трансформера, до 500× быстрее на CPU[^24^] | Радикально дешевле, но заметная потеря качества | Отклонён сейчас; кандидат для тестов/CI |

## 7. Выбранный подход

**Архитектура:** ModelWorker получает текст → проверяет точный кэш → при
промахе вызывает внешний embedding-сервис через собственный клиент за
интерфейсом `EmbeddingBackend` → сохраняет L2-нормированный вектор в кэш →
передаёт вектор в существующие `normalize`/`cosine`/`classify`.

```text
            ModelWorker (capability "model")
   +---------------------------------------------+
   |  аргументы: operation, text / vector, ...   |
   |                 |                           |
   |        [если задан text]                    |
   |                 v                           |
   |      EmbeddingCache (точный, LRU,           |
   |      лимит памяти, опц. TTL)                |
   |        | hit        | miss                  |
   |        v            v                       |
   |     вектор    EmbeddingBackend (interface)  |
   |                   |  OpenAI /v1/embeddings  |
   |                   v                         |
   |            TEI / Ollama / cloud API         |
   |                   |                         |
   |     L2-нормализация при записи в кэш        |
   |                 v                           |
   |   normalize / cosine / classify (уже есть)  |
   +---------------------------------------------+
```

Публичный контракт воркера (схема аргументов) расширяется полями `text`
(строка или массив) и опционально `model`; конфигурация backend'а (endpoint,
таймауты, лимит кэша, хеш-функция) — параметры конструктора/конфига воркера,
не Executor'а. Ошибки сервиса (недоступность, таймаут) выражаются исключениями
в том же стиле, что и существующие `std::invalid_argument`, — единый контракт
ошибок сохраняется.

**Почему именно так:**

- Один сетевой хоп вместо двух, Executor не меняется — архитектурный принцип
  «Worker — источник истины» сохранён (выбор В2 над В1).
- Кэш Никиты превращает «векторизацию при каждом вызове» в «векторизацию при
  первом вызове»: при hit rate 90–99 % средняя латентность падает на 1–2
  порядка, а повторные сравнения с эталонами становятся бесплатными.
- Вариант А (предвычисление) не теряется: прогрев кэша батчами — это тот же
  механизм, заполненный заранее; для статичных корпусов это даёт латентность
  варианта А при архитектуре варианта Б.
- Интерфейс `EmbeddingBackend` оставляет открытыми В3 (ONNX в процессе) и О8
  без изменения контракта воркера.

## 8. Риски и открытые вопросы для команды

- **Hit rate — гипотеза, требующая замера.** Все выигрыши кэша упираются в
  реальную повторяемость текстов. Первым шагом реализации добавить метрики
  (hits/misses, размер кэша) и решить про LRU→LFU по данным.
- **Недоверенные тексты.** Если вход может приходить извне, ключ кэша —
  SHA-256 (защита от сконструированных коллизий); если только внутренний
  контур — XXH3-128 быстрее[^18^]. Нужно решение команды по угроз-модели.
- **Единая модель для всего пайплайна.** Все тексты, участвующие в одном
  `cosine`/`classify`, должны быть векторизованы одной моделью; смена модели
  = новая «эпоха» кэша[^14^].
- **Конкурентный доступ.** Если Executor станет многопоточным, кэш потребует
  синхронизации (read-write lock или sharding) — заложить в интерфейс сразу.
- **Персистентность кэша** между запусками (дамп на диск) — не входит в MVP,
  обсуждается отдельно.
